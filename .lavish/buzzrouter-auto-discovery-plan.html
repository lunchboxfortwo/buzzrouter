Grounded research plan

Public evidence in. Safe listings out.

Auto-discovery should identify and verify Buzz relay hosts without probing private workspaces. Technical indexing is automatic; public descriptions and join behavior become administrator-controlled.

Recommendation

Build a provenance-driven relay index using NIP-66, public GitHub references, NIP-65 hints, and direct NIP-11 probes. Never enumerate hosted subdomains, query private events, or retain invite codes.

What the protocol actually allows

The product has to respect the difference between a relay being reachable and a community wanting to be promoted.

01 · IDENTITY

The URL is the community

Buzz binds a workspace to the relay host. A normalized origin is the durable candidate key; public keys identify people and agents, not the workspace.

02 · METADATA

NIP-11 proves software, not purpose

Buzz publishes an exact software URL, version, NIPs, relay identity, limits, and a public icon. Its name and description are currently generic.

03 · ACCESS

Hosted communities are invite-only

Knowing the relay URL does not grant membership. BuzzRouter must not redeem invites or query events to infer channels, members, or activity.

04 · DISCOVERY

Nostr already has relay monitors

NIP-66 is the broad discovery feed. NIP-65 and public source references add candidate hints. Direct probes remain the final authority.

Source strategy

Broad discovery is useful only when each source is treated as a hint, not a verdict.

The privacy boundary

This is the line that keeps a directory from becoming a private-workspace scanner.

Allowed public observations

  • NIP-11 relay information and public workspace icon
  • TLS validity, DNS answers, latency, and HTTP status
  • A WebSocket open and initial protocol behavior
  • Signed NIP-65 and NIP-66 events from configured relays
  • Public source provenance and administrator claims

Explicitly blocked

  • Messages, channels, members, agents, repos, or workflows
  • Invite redemption, retention, screenshots, or analytics
  • Certificate-transparency or dictionary subdomain enumeration
  • Builderlab account APIs or operator APIs without partnership
  • Private, loopback, link-local, or cloud metadata addresses

How listings become trustworthy

Auto-discovery handles the host. Administrator control handles public identity and join intent.

1. Technical verification

Exact block/buzz software metadata plus NIPs 29 and 42 and a successful WebSocket handshake.

2. Control proof

Custom domains use DNS TXT or .well-known. Hosted subdomains use a temporary admin-controlled NIP-11 icon challenge.

3. Public enrichment

The verified administrator supplies the actual name, description, categories, and public invite policy. Scraping cannot infer these safely.

Ranking without pretending to see inside

Community opinion, operational health, and popularity remain separate signals in the UI and database.

Bayesian quality, not raw stars

One signed rating per Nostr pubkey. A confidence prior prevents a single five-star rating from outranking an established community.

quality = (v / (v + m)) * R + (m / (v + m)) * C

m = 10 initial confidence prior

Four phases to a real MVP

The current GitHub Pages deployment remains the prototype until PostgreSQL and a continuously running worker exist.

Days 1-4

Safe technical index

Postgres, pg-boss, SSRF tests, NIP-11 probes, WebSocket checks, strict classifier.

Days 5-7

Automatic sources

NIP-66, GitHub adapter, NIP-65 hints, evidence review, publication rules.

Days 8-10

Claims and metadata

Nostr auth, DNS and HTTP proofs, hosted icon challenge, listing controls.

Days 11-14

Ratings and ranking

Bayesian quality, trending rollups, fraud caps, database-backed product views.
